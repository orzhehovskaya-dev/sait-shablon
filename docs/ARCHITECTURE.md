# Архітектура

## Стек

| Шар | Що | Навіщо |
|---|---|---|
| Сайт | Next.js 15 (App Router), TypeScript, React 19 | Швидкий сайт + серверні API в одному проєкті, хостинг на власному домені |
| Стилі | Власна CSS-дизайн-система (`app/globals.css`) | Усі кольори/шрифти — змінні в одному місці; без шаблонного вигляду |
| Шрифт | Inter Tight (кирилиця) | Щільний гротеск для великих заголовків у стилі fashion-агенцій і для тексту |
| База | Supabase (Postgres) | Бронювання, налаштування розкладу, журнал платежів; вхід в адмінку |
| Оплата | WayForPay (серверний підпис HMAC-MD5) | Твоя платіжна система |
| Календар | iCloud CalDAV | Читання зайнятості та запис зустрічей у твій Apple Calendar |
| Відео | Zoom Server-to-Server OAuth | Окреме посилання на кожну зустріч |
| Листи | Resend | Підтвердження, нагадування, скасування |
| Сповіщення | Telegram Bot API | Миттєве повідомлення про оплату |
| Хостинг | Vercel + cron-job.org | Деплой з GitHub, HTTPS, власний домен, планувальник |

## Двостороння синхронізація з iCloud: порівняння сервісів (перевірено 18.10.2026)

| Сервіс | Читає зайнятість з iCloud | Записує зустрічі в iCloud | Оплата | WayForPay |
|---|---|---|---|---|
| Cal.com | так (Apple ID + пароль застосунку) | так | Stripe, PayPal, Alby, HitPay | ні |
| Acuity Scheduling | так | так | Stripe, Square, PayPal | ні |
| Calendly | так (за даними спільноти Calendly) | так | Stripe, PayPal | ні |
| **Цей сайт** | **так (CalDAV, пароль застосунку)** | **так, в окремий календар** | **WayForPay** | **так** |

Готові сервіси синхронізуються з iCloud в обидва боки, але жоден не приймає оплату через WayForPay і не вміє тримати слот, доки оплата не пройде. Тому бронювання реалізоване на сайті з тим самим двостороннім підключенням до iCloud:

- **iCloud → сайт.** Перед показом слотів і перед кожним бронюванням сайт читає всі твої календарі iCloud: звичайні та повторювані події, винятки з серій, події на весь день. Події «Вільно» та скасовані не блокують час.
- **Сайт → iCloud.** Після підтвердженої оплати зустріч створюється в календарі «Мої зустрічі» з посиланням на Zoom і анкету. Після скасування чи повернення в адмінці подія видаляється.
- **Обмеження.** Якщо видалити або перенести подію зустрічі прямо в «Календарі» на iPhone, сайт не скасує бронювання і не поверне гроші автоматично — для цього є адмінка. Так задумано: випадкове видалення події не повинно скасовувати оплачену зустріч.
- **Надійність.** Якщо iCloud недоступний, слоти не показуються (а не показуються «на вдачу»).

## Процес бронювання

```
Клієнт: послуга → дата/час → 4 поля контактів + згода → «Оплатити»
  │
  ▼  POST /api/bookings
Сервер: перевіряє анкету → бере СВІЖУ зайнятість з iCloud → перевіряє слот
        → записує бронювання зі статусом «очікує оплату» (утримання 20 хв)
        → база відхиляє запис, якщо час уже зайнятий (правило no_overlap)
        → підписує платіж і віддає поля форми WayForPay
  │
  ▼  secure.wayforpay.com
WayForPay ──► POST /api/wayforpay/callback   (перевірка підпису, суми, валюти)
          └─► клієнт повертається на /booking/result (сторінка опитує статус;
              якщо сповіщення ще немає — сервер сам питає CHECK_STATUS)
  │
  ▼  статус «оплачено» (один раз, навіть якщо сповіщень кілька)
Zoom-зустріч → подія в iCloud → лист клієнту (.ics + посилання на анкету) → Telegram тобі
  │
  ▼  клієнт заповнює анкету на сторінці результату (або за посиланням із листа)
Анкета зберігається → друге Telegram-повідомлення «Анкету заповнено»
Кожен крок записується окремо; якщо щось не вдалося — планувальник повторює.
```

## Захист від подвійних бронювань

1. Сервер перевіряє слот зі свіжими даними календаря перед записом.
2. У базі діє обмеження `no_overlap`: два активні бронювання (разом із 30-хв перервою) фізично не можуть перетинатися — навіть якщо два клієнти натиснуть «Оплатити» в ту саму секунду.
3. Прострочені утримання звільняються автоматично.

## Безпека і персональні дані

- Секрети (ключ WayForPay, service role Supabase, токени) — лише в змінних середовища сервера.
- Таблиці бази закриті для публічного доступу (RLS + відкликані права); сайт працює з базою лише з сервера.
- Адмінка: вхід через Supabase Auth + перевірка ролі (`owner` / `assistant`) на кожній сторінці й дії. Повернення, скасування й налаштування — лише для `owner`.
- Telegram — лише в особистий чат, повна анкета — за посиланням в адмінку після входу.
- Аналітика — тільки після згоди, без персональних даних.
- Публічні посилання на статус/календар використовують випадковий 192-бітний токен, а не номер бронювання.
- Обмеження частоти запитів і пастка для ботів на формі; захист CSV від формул.
